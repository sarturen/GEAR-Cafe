# GEAR Framework Runtime Contract v1

Status: **Frozen for v1 implementation — 2026-09-18 revision**
Contract id: `gear.runtime/v1`
Date: 2026-09-18

This contract supersedes older Runtime conclusions. Exact Python names and
shapes are [api.py](../contracts/gear_contracts/api.py) and
[data.py](../contracts/gear_contracts/data.py).

## 1. Control session and worker

A Control Host runs one GEAR session, GUI or CLI. Before Plugin loading, acquire
a host-wide process-owned OS exclusion handle and hold it until process exit.
The Windows default is a named mutex `Global\GEAR.ControlSession.v1`.
If the handle cannot be acquired, exit with HOST_BUSY. Do not continue unlocked
or use a stale-prone persistent busy flag as the exclusion mechanism.

One fixed Framework worker serializes Plugin factories, configuration, static
validation, Run calls, cleanup and session shutdown. Plugin-owned acquisition
threads remain the Plugin's responsibility.

Only one accepted submission exists at a time. Reject a second submission with
`GearError("BUSY", message)`; do not queue it. Outstanding manual operations or
configuration application must also finish before accepting a Run.
Session-owned passive acquisition/status caches may continue; they are not
independent test execution or permission to inject manual hardware commands.

## 2. Application API

Use `FrameworkV1`. API methods may be called from GUI/CLI threads; they do not
wait for a Plugin hardware call. Input arguments to `submit` are absolute local
paths to UTF-8 YAML files, not mappings or Plugin instances.

### submit

Atomically reserve the Run slot and return an opaque unique id. On the worker,
copy the three files into the Run directory, then parse and validate the copies.
Read/parse/configuration failures reject the submission without a test result.

The archived Environment must equal the control session's loaded Environment
as data. Otherwise reject with ENVIRONMENT_MISMATCH; do not silently reconfigure
long-lived connections. GUI edits are persisted/applied before submission.
CLI loads its selected Environment when creating the session. Loading a different
Environment is an explicit idle operation.

Preflight checks only configuration. It neither probes hardware nor uses live
or cached online/offline status to gate the Run. Valid configuration for an
offline device still passes Preflight.

### confirm

Only WAITING_CONFIRMATION accepts `confirm(run_id)`. Other states raise
INVALID_STATE, so duplicate confirmation cannot execute twice.
Set `execution_started: true` immediately before Plugin Run preparation, or
before the first DSL step when no Plugin is involved. Preparation errors
thereafter are executed failures.

### stop

Record the request and return promptly:

- Before execution starts, decline the submission: outcome DECLINED, result null.
  Let any in-progress static callback return before finalization.
- During execution, request the token. Framework waits and loops observe it;
  an in-flight Plugin call is allowed to return.
- Preserve the first recorded terminating cause. A recorded FAIL never becomes
  STOPPED. A stop accepted before a later call returns yields STOPPED; any later
  call error is secondary diagnostic information.
- After FAIL, human stop may skip evidence requests not yet started. Record
  EVIDENCE_CANCELLED for each skipped request. Do not kill in-progress collection.
- During FINALIZING, stop does not change an already-known outcome. It may only
  cancel not-yet-started evidence after FAIL; cleanup/reporting still proceed.
- Cleanup always proceeds, even with the token requested.
- Repeated stop, including on a completed known Run, is a no-op.

A Plugin raising `StopRequested` is cancellation only if its token was requested;
otherwise treat it as an unexpected Plugin exception.

### status and subscriptions

`get_status` returns a detached `RunStatus` dictionary. Its Preflight report
supplies the confirmation UI's bindings and coverage. `report_path` is an
absolute path and remains null until the final report is successfully published.
A partial/temporary file is not a saved report. A blocked session raises
HOST_BLOCKED for new Runs/manual commands; its Workspace state stays ACTIVE.

`subscribe` registers `listener(event: RunEvent) -> None`. Callbacks run
serially on the Framework worker in per-Run sequence order. No replay is offered.
Subscribe before submission and use `get_status` for the latest snapshot.
Listeners return promptly and must not wait for work on the same worker.
Listener exceptions are logged without altering the test or interrupting others.

`unsubscribe` is idempotent and thread-safe. After it returns, no new callback
starts for that subscription; an already-started callback may finish.
GUI Shell translates notifications to GUI-thread signals. Workspace listeners
always run on the GUI thread.

Unknown ids raise UNKNOWN_RUN; invalid command/state combinations raise
INVALID_STATE. Construct boundary errors as `GearError(code, message)`, with
both arguments strings. The first argument is the stable machine-readable code.

## 3. State and complete finalization

| Run phase | Meaning |
|---|---|
| PREFLIGHT | Archiving/parsing/static checks. |
| WAITING_CONFIRMATION | Static checks passed; execution has not started. |
| RUNNING | Plugin Run preparation or DSL execution. |
| FINALIZING | Evidence, cleanup, reporting or Run-task exit remains. |
| FINISHED | All finalization succeeded and the entire task exited; the slot may be released. |
| BLOCKED | Finalization failed; this session permits no further execution. |

`outcome` is initially null, then REJECTED, DECLINED, PASS, FAIL or STOPPED.
`result` is null for REJECTED/DECLINED; otherwise it is the current/final test
result. `execution_result` preserves the execution conclusion before
finalization, without rewriting it when finalization fails. Both start null.
A provisional PASS can become FAIL under section 3.1.
An outcome may be known while `active` remains true.

`session_blocked` starts false and latches true on finalization failure.
`finalization_errors` starts empty and accumulates exact FinalizationFailure
records in occurrence order. Status and report expose these same fields.

Rejected/declined submissions also finalize their submission resources.
Only complete task exit permits FINISHED and IDLE. A result alone does not.

Before return, the Run task must join Plugin Run-local work, dispose Run
subscriptions, close artifact/event writers and finish the final report.
Only after successful finalization and return may the coordinator publish
FINISHED and accept the next Run. Failed finalization never releases the slot.
Long-lived session observers/connections survive, but must retain no stale Run
context and must not write into the completed Run.

### 3.1 Finalization failure and explicit records

Plugin cleanup, Framework cleanup, event-writer finalization or final-report
persistence failure blocks the session. BLOCKED is a lifecycle state, not a
fourth test-result category.

| Execution conclusion | Final result after finalization failure |
|---|---|
| PASS | FAIL; retain execution_result PASS. |
| FAIL | FAIL; retain the original primary failure. |
| STOPPED | STOPPED; append finalization errors separately. |
| No execution (REJECTED/DECLINED) | null; retain the submission outcome. |

When PASS changes to FAIL, set outcome FAIL and create primary_failure with
phase `finalization`, null step/resource ids, and the first finalization
diagnostic. Never overwrite an existing primary failure. After STOPPED, record
finalization errors without inventing a new execution failure.

Latch session_blocked immediately and retain active true. Attempt remaining
cleanup/reporting once, recording every additional failure. Do not force-kill
Plugin calls, automatically recover/reconnect/retry, or start another round of
device evidence because finalization itself failed. After the worker's attempt
returns, publish BLOCKED, not FINISHED/IDLE. If a call has not returned, remain
FINALIZING with the slot occupied; do not invent a timeout or claim exit.

Every FinalizationFailure records:
- stage: plugin_cleanup, framework_cleanup, event_write or report_write;
- plugin_id: the responsible Plugin id, or null for Framework work;
- timestamp: actual UTC ISO 8601 time ending in Z;
- diagnostic: stable code, readable message and original supporting details.

Use codes PLUGIN_CLEANUP_FAILED, FRAMEWORK_CLEANUP_FAILED, EVENT_WRITE_FAILED and
REPORT_WRITE_FAILED. When wrapping a Plugin error preserve its original code
in diagnostic.details. For exceptions, details must include operation,
exception_type, exception_message and traceback; include affected paths/resource
ids when available. A generic "cleanup failed" without original information is
insufficient.

The GUI/CLI displays Run id, execution_result, final result, stage/message and:
"Finalization failed. Further execution is blocked. Resolve the cause and restart
GEAR." Show the original execution failure separately. Status display may remain
available; configuration/manual controls stay disabled. Restart does not
automatically rerun the test or repair hardware.

Publish a report only after its temporary file was successfully written/closed
and atomically replaced the final file. If writing fails, report_path remains
null. Never label a partial file or stale provisional PASS as the final report.
In-memory status and GUI/CLI still contain the revised result and ordered errors.

Also attempt one append of the failure record, Run id, original/final results and
blocked flag to ordinary `logs/session.log` under the application directory.
This is one local log, not a recovery service. If that write also fails, expose
its error in the current GUI/CLI (stderr for CLI), retain diagnostics in memory
and explicitly say that they were not persisted. Do not recursively log that
logging failure or claim durability when all writes failed.

Timestamp meanings are explicit: execution_finished_at is when the execution
conclusion became known; reported_at is report construction time. Neither claims
that the later Run-task exit has already occurred.

Example relevant status fields (all other RunStatus keys remain required):

```json
{
  "phase": "BLOCKED",
  "execution_result": "PASS",
  "outcome": "FAIL",
  "result": "FAIL",
  "active": true,
  "session_blocked": true,
  "report_path": null,
  "finalization_errors": [{
    "stage": "report_write",
    "plugin_id": null,
    "timestamp": "2026-09-18T09:30:00Z",
    "diagnostic": {
      "code": "REPORT_WRITE_FAILED",
      "message": "Could not publish the final report: no space left.",
      "details": {
        "operation": "publish_report",
        "path": "runs/example/report.json",
        "exception_type": "OSError",
        "exception_message": "No space left on device",
        "traceback": "<captured traceback from this exception>"
      }
    }
  }]
}
```


## 4. Plugin invocation and shutdown

Startup creates one Plugin Runtime object per Plugin. Factory creation and
initial configuration do not open/probe hardware. While idle, the Workspace may
explicitly connect/use the same Plugin's services.

For a confirmed Run:

1. Resolve Plugins involved in execution and evidence.
2. In ascending Plugin-id order call `begin_run`, passing the complete archived
   slice, sorted involved resource ids and a fresh Run context.
3. Execute setup, body and normal-success teardown according to the DSL.
4. On execution FAIL collect declared evidence in declaration/expansion order.
5. Call `end_run` in reverse attempted begin order, including a Plugin whose
   begin failed after partial preparation.
6. Finish Framework Run-local work, report and the complete Run task.

Attempt remaining cleanup even when one end call fails. Do not call session
`close` at Run end and do not recreate device services per Test Case.
If an evidence-only Plugin could not prepare, record its requests as failed
and continue with other evidence; never call an unprepared session.

At application shutdown, stop/finalize the Run, finish manual work, dispose
Workspaces on the GUI thread and close sessions in reverse creation order on
the worker. Retain host exclusion until process exit. Tab changes do not dispose
Workspaces or release connections.

## 5. Exact data and context conventions

Use the ordinary dictionaries in data.py. Include every required key, including
empty objects/lists and null values. Only NotRequired keys may be omitted.
JSON numbers are finite. Binary content goes into files.
Inputs are detached snapshots; receivers must not mutate them.

Contexts implement the exact attributes/methods in api.py. Attributes are
read-only to Plugins. `monotonic()` returns seconds from the Executor's clock.
`StopToken.is_requested()` is thread-safe. `wait(timeout_s)` waits up to a
nonnegative number of seconds, wakes early on stop, and returns whether requested.

`artifact_dir` is the absolute Run-directory path. Write artifacts under
`evidence/<plugin-id>/`. Return relative forward-slash paths inside that root;
use distinct names for different captures.

`step_path` identifies a source YAML node, e.g. `/body/0/steps/1` or
`/evidence_on_fail/0`, with zero-based list indexes. `iteration` is one-based
inside Repeat and otherwise null. `call_id` is unique within the Run.
The Plugin documents state-vs-event condition semantics and resets Run-specific
observation cursors in `begin_run`.

`emit(diagnostic)` is a thread-safe diagnostic sink attributed by the host to
the Plugin and Run. End all Run-local emitters before `end_run` returns; no
emission is allowed after Run end. It is not a general event bus.

## 6. Preflight and coverage

Preflight validates archived schemas, ids, capabilities, arguments, bindings,
wildcards, device declarations and involved Plugin slices. It validates the full
slice of each involved Plugin; INCOMPLETE/INVALID rejects that Run. Unrelated
installed Plugins do not gate it.

This preserves a simple Plugin-wide validation boundary. An unfinished extra
binding in an involved slice can block that Plugin's Run. To leave a Project
target uncovered, omit its Environment binding; malformed bindings are not
silently ignored.

Each CoverageItem corresponds to a capability-request source path and a concrete
Project resource. `bound` records static resolution; `executed` becomes true
only when actually called. Missing wildcard bindings remain explicit false/false
items. Reject zero-bound wildcards. Display partial coverage before confirmation
and in the final report. PASS does not imply full Project coverage.

## 7. Events and reports

```text
runs/<run-id>/
  input/test-case.yaml
  input/project.yaml
  input/environment.yaml
  preflight.json
  events.jsonl
  evidence/<plugin-id>/...
  report.json
```

No database or Plugin package snapshots are required; record installed Plugin
ids and versions.

Each events.jsonl line is a RunEvent. Sequence starts at 1 and increments by one.
Timestamps are UTC ISO 8601 strings ending in Z. elapsed_s is monotonic elapsed
time since submission. Unrelated step_path/resource_id fields are null.

| Event | Required details fields |
|---|---|
| run.state | outcome, result, execution_started |
| step.start | kind, iteration |
| step.end | kind, iteration, ok, diagnostic |
| condition.sample | condition, iteration, call_id, started_s, finished_s, result |
| operation.result | operation, iteration, call_id, result |
| wait.chosen | duration_s, iteration |
| plugin.diagnostic | plugin_id, diagnostic |
| evidence.result | capability, call_id, result |
| cleanup.diagnostic | plugin_id (or null), diagnostic |
| finalization.failure | failure (FinalizationFailure), execution_result, result, session_blocked |

Result dictionaries use shared types; diagnostic is Diagnostic or null.
Plugin details remain opaque. Sampling events record actual start/finish times
relative to submission, never ideal scheduled times.

On success, persist the outcome event while FINALIZING, close the event writer,
then atomically publish report.json as the task's last fallible operation.
Do not defer cleanup until after report publication. After task return, publish
FINISHED only in process with the next sequence number; do not reopen the log.
There is no durable event replay requirement.

Before event-writer close, append finalization.failure when writing is possible.
If the event writer or report fails, do not reopen/retry that writer; emit the
diagnostic in process and use section 3.1's session-log/display fallback.
A failed write does not promise durable events.

Report shape is RunReport with api gear.report/v1. Input/event/artifact paths in
reports are relative to the Run directory. Rejected/declined submissions have
null results and are reportable when archival succeeded. Coverage, primary
failure, evidence and cleanup diagnostics remain distinct facts.
Report execution_result, final result, session_blocked and every finalization
error separately. cleanup_diagnostics holds cleanup information; the ordered
finalization_errors additionally attribute stage, Plugin and occurrence time.

## 8. Acceptance checks

A Framework implementation must verify:

- sequential Runs reuse the same Plugin/device connection and reset tokens/state;
- Preflight never gates on actual or cached device availability;
- cancellation before execution yields no result;
- stop waits for in-flight calls and cannot erase a recorded FAIL;
- no new Run/manual command overlaps evidence, cleanup, report writing or exit;
- a second GUI/CLI process is refused throughout the control-session lifetime;
- Workspace callbacks run on GUI thread and Plugin calls on the worker;
- partial preparation receives cleanup;
- wildcard gaps survive both Preflight and final reporting;
- FINISHED occurs only after successful finalization and entire task return;
- successful execution followed by cleanup failure records PASS -> FAIL;
- finalization after FAIL/STOPPED retains that result and the primary failure;
- every finalization error retains stage, time, Plugin and original exception;
- report failure leaves report_path null with visible/session-log diagnostics;
- blocked sessions reject subsequent Runs and manual commands;
- report plus session-log write failure is disclosed as not persisted.
