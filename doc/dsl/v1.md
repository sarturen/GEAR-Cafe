# GEAR Flow DSL Contract v1

Status: **Frozen for v1 implementation**
Contract id: `gear.dsl/v1`
Date: 2026-09-18

This document is normative. The words **MUST**, **MUST NOT**, **SHOULD**, and
**MAY** describe conformance requirements.

## 1. Scope

GEAR Flow DSL describes one independent Test Case over logical resources. It is
a YAML-serialized task-flow language for:

```text
operation → wait → validation → bounded repetition
```

It is not a programming language, device configuration language, scheduler,
state machine, or data-processing language.

Framework owns this grammar and all temporal semantics. Plugins contribute only
the names and argument schemas of operations, conditions, and evidence
capabilities.

## 2. Canonical document

A Test Case is one UTF-8 YAML document:

```yaml
api: gear.dsl/v1
name: kl30_boot_stability

setup:
  - do:
      resource: POWER.kl30
      operation: ON

body:
  - assert:
      all:
        - resource: SCREEN.center
          condition: LIT
        - resource: ADB.main
          condition: AVAILABLE
      within: 30s
      every: 200ms

  - assert:
      all:
        - resource: SCREEN.center
          condition: NOT_BLACK
        - resource: ADB.main
          condition: AVAILABLE
      for: 1h
      every: 100ms

teardown:
  - do:
      resource: POWER.kl30
      operation: OFF

evidence_on_fail:
  - resource: ADB.main
    evidence: DIAGNOSTIC_LOGS
  - resource: SCREEN.center
    evidence: SCREENSHOT
```

Required top-level fields:

| Field | Rule |
|---|---|
| `api` | MUST equal `gear.dsl/v1`. |
| `name` | MUST match `[A-Za-z][A-Za-z0-9_-]*`. |
| `body` | Required non-empty list of steps. |

Optional top-level fields:

- `description`: human-readable string;
- `setup`: list of steps, default empty;
- `teardown`: list of steps, default empty;
- `evidence_on_fail`: list of evidence requests, default empty.

Unknown fields MUST be rejected. Duplicate YAML keys MUST be rejected. YAML
anchors, aliases, custom tags, and executable constructors MUST be rejected.

## 3. Values and identifiers

Resource references use:

```text
<RESOURCE_TYPE>.<alias>
<RESOURCE_TYPE>.*
```

Resource Types and capability names match `[A-Z][A-Z0-9_]*`. Aliases match
`[A-Za-z][A-Za-z0-9_-]*`.

Arguments are JSON-compatible YAML values only. No implicit YAML timestamps,
sets, binary nodes, or non-string mapping keys are allowed.

Durations use a positive decimal number followed immediately by one unit:

```text
ms  s  m  h
```

Examples: `200ms`, `5s`, `1.5m`, `1h`. Framework converts durations to an
internal monotonic-clock representation. Calendar units are forbidden.

## 4. Step union

Every step mapping MUST contain exactly one of:

```text
do
wait
assert
repeat
```

No step may contain multiple step kinds.

## 5. `do`

Shape:

```yaml
- do:
    resource: ADB.main
    operation: SHELL
    args:
      command: getprop ro.build.version.release
```

Rules:

- `resource` MUST be a concrete logical resource; wildcards are forbidden;
- `operation` MUST be declared by that Resource Type's Plugin;
- `args` defaults to `{}` and MUST satisfy the Plugin's `args_schema`;
- the call is synchronous from Framework's perspective;
- a failed result or uncaught exception after Runtime starts causes `FAIL`;
- returned data is logged for diagnostics but cannot be assigned or referenced
  by later DSL steps.

If command output must affect the result, the Plugin must make the operation
fail by its declared semantics or expose a semantic condition. DSL provides no
generic stdout, regex, parsing, or variable features.

## 6. `wait`

Fixed wait:

```yaml
- wait:
    duration: 5s
```

Randomized wait:

```yaml
- wait:
    random:
      min: 5s
      max: 30s
```

Exactly one of `duration` or `random` is required. For `random`, `min` MUST be
less than or equal to `max`. Framework chooses one duration in the inclusive
range and records the chosen value in Run events.

Wait uses a monotonic clock and is cooperatively stoppable.

## 7. `assert`

Immediate assertion:

```yaml
- assert:
    all:
      - resource: SCREEN.center
        condition: LIT
```

Each condition item contains:

| Field | Rule |
|---|---|
| `resource` | Concrete logical resource or Resource Type wildcard. |
| `condition` | Plugin-declared condition name. |
| `args` | Optional object, default `{}`, validated against Plugin schema. |

`all` MUST be a non-empty list. It is the only v1 boolean composition: every
expanded condition in the assertion must be satisfied together. v1 has no
`or`, general `not`, parentheses, or precedence rules. Negative meanings use
explicit Plugin conditions such as `NOT_BLACK` or `UNAVAILABLE`.

Within one sampling cycle, Framework evaluates expanded conditions sequentially
in declaration order and does not short-circuit ordinary unsatisfied results.
The cycle succeeds only if every result is `ok: true, satisfied: true`. This is
one logical sampling cycle, not a claim that hardware was observed at an
identical physical instant. An `ok: false` result or exception ends the
assertion immediately with Run `FAIL`.

An assertion has exactly one timing mode.

### 7.1 Immediate mode

If `within`, `for`, and `every` are absent, Framework evaluates the complete
assertion once. Any unsatisfied condition causes `FAIL`.

### 7.2 `within` mode

```yaml
- assert:
    all:
      - resource: SCREEN.center
        condition: LIT
      - resource: ADB.main
        condition: AVAILABLE
    within: 30s
    every: 200ms
```

Framework evaluates the complete assertion immediately, then at each `every`
interval. It succeeds when all conditions are simultaneously satisfied at one
sampling point. If not satisfied earlier, Framework performs a final evaluation
at the deadline. Failure at the deadline causes `FAIL`.

### 7.3 `for` mode

```yaml
- assert:
    all:
      - resource: SCREEN.center
        condition: NOT_BLACK
      - resource: ADB.main
        condition: AVAILABLE
    for: 1h
    every: 100ms
```

Framework evaluates immediately, at each `every` interval, and once at the end
deadline. Every evaluation MUST satisfy all conditions. The first unsatisfied
evaluation causes `FAIL`; otherwise the assertion succeeds after the full
duration.

### 7.4 Timing rules

- `within` and `for` are mutually exclusive;
- `every` is mandatory with either temporal mode;
- `every` is forbidden for an immediate assertion;
- all durations MUST be greater than zero;
- Framework uses a monotonic clock;
- evaluations do not overlap;
- if evaluation takes longer than `every`, Framework starts the next evaluation
  as soon as the previous one returns; it does not create concurrent calls;
- the recorded event timeline reflects actual sampling times;
- a Plugin may use continuous/event-driven observation internally, but its
  condition result at each Framework call must obey its declared semantics.

## 8. `repeat`

```yaml
- repeat:
    count: 10000
    steps:
      - do:
          resource: POWER.kl15
          operation: OFF
      - wait:
          duration: 5s
      - do:
          resource: POWER.kl15
          operation: ON
```

Rules:

- `count` MUST be a positive integer;
- `steps` MUST be a non-empty list of valid steps;
- `steps` may contain `do`, `wait`, and `assert`; nested `repeat` is forbidden
  in v1;
- iteration numbering in events is one-based;
- no `break`, `continue`, `while`, or `until` exists;
- the first failed child step ends the Repeat and the Test Case.

## 9. Resource wildcard and coverage

`<RESOURCE_TYPE>.*` is allowed only in assertion condition items and evidence
requests. It expands to all resources of that type declared by Project.

Wildcard expansion order is ascending lexical logical-resource id. This makes
condition evaluation, evidence collection, and event output deterministic
without depending on YAML mapping order.

For each Project resource:

- if Environment has a valid binding, Framework evaluates or collects it;
- if Environment lacks a binding, Framework records an explicit coverage gap;
- missing bindings are never silently treated as success.

A partially bound wildcard may execute against its valid bindings while the Run
report preserves the uncovered Project resources.

If a wildcard resolves to zero valid bindings, Preflight MUST reject the Test
Case. No assertion over an empty set may pass vacuously.

Concrete resources required by `do` or `assert` MUST have valid Environment
bindings; otherwise Preflight rejects the submission.

## 10. Evidence declaration

Failure evidence is a declarative top-level list, not executable failure flow:

```yaml
evidence_on_fail:
  - resource: ADB.main
    evidence: DIAGNOSTIC_LOGS
    args:
      category: system
  - resource: SCREEN.*
    evidence: SCREENSHOT
```

Rules:

- evidence names and argument schemas come from Plugins;
- concrete references and wildcards follow the same coverage rules as
  assertions;
- evidence is collected only after `FAIL`;
- it is not automatically collected after `STOPPED`, Preflight rejection, or
  declined confirmation;
- collection proceeds best effort in declaration/expansion order;
- one evidence failure does not stop later evidence requests;
- evidence failure never replaces the original failure;
- evidence capabilities SHOULD preserve incident state and MUST NOT be used as
  an arbitrary recovery workflow.

## 11. Lifecycle semantics

Execution order after successful Preflight and human confirmation:

```text
setup → body → teardown
```

`teardown` runs only if `setup` and `body` complete normally. It does not run
after `FAIL` or `STOPPED`. Framework cleanup always runs and remains distinct
from DUT teardown.

Test Cases MUST be independently executable. They may not depend on another
Test Case's output, execution order, or hidden global state.

## 12. Preflight

Before execution, Framework MUST reject a Test Case when:

- YAML or DSL structure is invalid;
- an identifier or duration is invalid;
- a Project resource does not exist;
- a required concrete Environment binding is missing or invalid;
- a wildcard has zero valid bindings;
- the responsible Plugin or Resource Type is unavailable;
- a requested capability is undeclared;
- arguments do not match the capability schema;
- a referenced `device` id is undeclared;
- any involved Plugin slice validates as `INCOMPLETE` or `INVALID`.

Preflight MUST NOT open or probe hardware. An offline ADB device, unavailable
COM port, missing camera frame, or unstable link is discovered only at Runtime.

Preflight rejection creates no test result:

```yaml
execution_started: false
result: null
```

## 13. Runtime result semantics

Once Runtime begins, only three top-level results exist:

| Result | Meaning |
|---|---|
| `PASS` | All requested execution and validation completed successfully. |
| `FAIL` | Any unexpected condition occurred after execution began. |
| `STOPPED` | A human explicitly requested cooperative stop. |

`FAIL` includes assertion failure, unavailable devices, link loss, operation or
condition failure, Plugin exception, and Framework execution exception. v1 has
no separate top-level `ERROR` result and no automatic retry/recovery policy.

The first failure remains primary. Later evidence or cleanup diagnostics are
secondary report facts.

## 14. Complete reference example

```yaml
api: gear.dsl/v1
name: kl15_sleep_wakeup_10000
description: Repeated KL15 off/on transition and recovery validation.

setup:
  - do:
      resource: POWER.kl30
      operation: ON

body:
  - repeat:
      count: 10000
      steps:
        - do:
            resource: POWER.kl15
            operation: OFF

        - assert:
            all:
              - resource: SCREEN.center
                condition: BLACK
              - resource: ADB.main
                condition: UNAVAILABLE
            within: 30s
            every: 200ms

        - wait:
            random:
              min: 5s
              max: 30s

        - do:
            resource: POWER.kl15
            operation: ON

        - assert:
            all:
              - resource: SCREEN.center
                condition: LIT
              - resource: ADB.main
                condition: AVAILABLE
            within: 60s
            every: 200ms

        - assert:
            all:
              - resource: SCREEN.center
                condition: HEALTHY
              - resource: ADB.main
                condition: AVAILABLE
            for: 30s
            every: 200ms

teardown:
  - do:
      resource: POWER.kl15
      operation: OFF
  - do:
      resource: POWER.kl30
      operation: OFF

evidence_on_fail:
  - resource: ADB.main
    evidence: DIAGNOSTIC_LOGS
  - resource: SCREEN.center
    evidence: SCREENSHOT
  - resource: CONSOLE.main
    evidence: BUFFER_DUMP
```

## 15. Parser and Executor conformance checklist

A v1 DSL implementation MUST test at least:

- accepted canonical documents for every step and timing mode;
- rejection of unknown/duplicate fields and unsafe YAML features;
- identifier, duration, argument-schema, and capability validation;
- immediate, `within`, and `for` sampling semantics;
- non-overlapping slow condition evaluation;
- fixed and randomized waits with recorded chosen duration;
- bounded Repeat behavior, nested-Repeat rejection, and first-failure termination;
- concrete-resource and wildcard resolution;
- partial coverage reporting and zero-binding rejection;
- setup/body/teardown lifecycle;
- declarative evidence ordering and primary-failure preservation;
- cooperative Stop and `PASS`/`FAIL`/`STOPPED` mapping.

## 16. Explicitly unsupported syntax

The following are outside v1:

```text
variables and assignments
step output references
generic stdout/stderr/exit-code expressions
generic regex, text, file, or math processing
OR, generic NOT, and arbitrary boolean expressions
IF / ELSE
WHILE / UNTIL
break / continue
functions or includes
cross-case state or dependencies
arbitrary resource tags/groups
wildcard operations
arbitrary on-failure step lists
automatic retry or recovery
Suite/Campaign scheduling
runtime Agent decisions
```
