# GEAR Project and Environment Contract v1

Status: **Frozen for v1 implementation — long-lived connection bindings**
Contract ids: `gear.project/v1`, `gear.environment/v1`
Date: 2026-09-18

This document defines the minimum shared data model used by DSL, Framework,
Plugin Runtime, and Plugin Workspaces.

## 1. Project

Project declares logical resources independent of one physical bench:

```yaml
api: gear.project/v1
name: cockpit_system

resources:
  POWER.kl30:
    type: POWER
  POWER.kl15:
    type: POWER
  ADB.main:
    type: ADB
  CONSOLE.main:
    type: CONSOLE
  SCREEN.center:
    type: SCREEN
  SCREEN.cluster:
    type: SCREEN
```

Rules:

- `api`, `name`, and non-empty `resources` are required;
- logical resource ids and types follow the Plugin/DSL v1 identifier rules;
- the id prefix MUST equal `type`;
- Project contains no COM ports, serial numbers, camera ids, ROI coordinates,
  relay channels, or Plugin configuration;
- v1 has no variants, profiles, tags, or controlled resource groups.

## 2. Environment

Environment describes one human-configured Bench:

```yaml
api: gear.environment/v1
name: bench_01

devices:
  ABC123: {}
  XYZ789: {}

plugins:
  gear.adb:
    config: {}

  gear.camera:
    config: {}

  gear.relay:
    config:
      controllers:
        main:
          port: COM7
          channels: 8

resources:
  ADB.main:
    type: ADB
    plugin: gear.adb
    device: ABC123
    config: {}

  POWER.kl30:
    type: POWER
    plugin: gear.relay
    device: ABC123
    config:
      controller: main
      channel: 1

  SCREEN.center:
    type: SCREEN
    plugin: gear.camera
    device: ABC123
    config:
      camera_id: camera-2
      roi: {x: 120, y: 80, width: 800, height: 480}
```

Required fields are `api`, `name`, `plugins`, and `resources`. Names are
non-empty strings. `devices` defaults to an empty mapping. Device keys are
non-empty, case-sensitive, opaque strings, with canonical empty-object values.
A Plugin record contains `config`, which defaults to an empty object.
Every saved resource has `type`, `plugin`, object `config` (default empty), and
optional string `device`. Its Plugin record must exist.

All documents obey the Plugin contract's YAML 1.2/JSON-compatible values,
duplicate-key rejection and common-envelope rules. Plugin config contents remain
opaque. Missing physical bindings are allowed; malformed outer records are not.

## 3. Device identity

Keys under `devices` are manually declared ADB serial strings. They are paper
identities used to group resources belonging to the same physical DUT.

- existence does not assert that ADB is online;
- live discovery does not automatically change this mapping;
- each resource has at most one `device` value;
- a resource may remain unassigned while configuration is incomplete;
- changing/deleting an id does not cascade to resource records;
- dangling values remain persisted until a human reconfigures them;
- Preflight rejects a dangling value for resources involved in a Run.

The `devices` mapping has no v1 metadata requirements. `{}` is the canonical
value. Additional device metadata is reserved for a future contract revision.

## 4. Plugin and resource configuration

`plugins.<plugin-id>.config` stores configuration shared by that Plugin's
resources. `resources.<logical-id>.config` stores one binding's configuration.
Both are opaque to Framework and owned by the Plugin.

Framework understands only:

```text
Plugin id
logical resource id
Resource Type
optional device id
Plugin-level config boundary
resource-level config boundary
```

Each Environment resource MUST exist in Project with the same type when used by
a Run. Each `plugin` MUST be installed and declare ownership of that Resource
Type.

Environment may persist incomplete or invalid Plugin configuration. Plugin
static validation and Framework outer validation determine executability.

Installed but not yet configured Plugins receive an empty slice:
`{"plugin": {"id": "<installed-id>", "config": {}}, "resources": {}}`.
For the ADB owner also include the saved `devices` mapping (empty by default).
This does not create hardware connections or silently save a new Plugin record.
The first Workspace commit persists the record. A Run using an absent binding
still follows ordinary missing-binding rejection/coverage rules.

## 5. Workspace persistence

GUI hosts one page per Plugin. The page owns the complete slice containing its
Plugin record and all resources assigned to it.

The Plugin that declares the `ADB` Resource Type additionally owns the
Environment's `devices` mapping. Every other Workspace receives the saved ids as
a read-only choice list and may only change `device` fields in its own resource
records.

On each semantic change, Workspace submits a complete replacement slice. Host
atomically persists the resulting Environment file. There is no Save/Cancel,
field patching, or dirty-state protocol.

The host MUST reject a replacement slice that attempts to modify another
Plugin's record or resources, or attempts to modify `devices` without owning
the `ADB` Resource Type. It MUST preserve unrelated slices semantically even if
YAML formatting is regenerated.

### 5.1 Exact slice projection and replacement

To project a Plugin slice, copy that Plugin's id/config record and all Environment
resources whose `plugin` equals its id. Keep resource ids as mapping keys;
remove the redundant `plugin` field from each slice resource. Include `devices`
only for the unique ADB owner. `PluginSlice` in the shared package fixes the keys.

For a replacement, first validate ownership/common fields. Remove only that
Plugin's previous resources, insert its new resources with the owning `plugin`
field restored, and replace its Plugin config. Reject stealing an existing
resource id from a different Plugin. Preserve other slices; ADB device removal
does not cascade into their associations.

During ACTIVE, reject commits and manual commands even if a Workspace leaves
controls enabled. A successful commit is persisted before notifications and
scheduled Plugin configuration application. No Run starts until that application
finishes. Persistence failure leaves the previous saved/current Environment.

## 6. Run snapshot

At submission, Framework copies Test Case, Project, and Environment into the Run
directory. That archived Environment is the sole binding input for the Run.

The archived Environment must equal the session's loaded Environment as data.
A mismatch is rejected, not automatically applied to live connections.
Configuration cannot change during ACTIVE, so the snapshot and reused device
services have the same selected bindings. Runtime always receives the archived
slice. Plugins do not re-read mutable GUI state.

Explicit idle-time loading/configuration changes may release affected old
connections; unchanged connections remain available. Run completion releases
only Run-local state, not long-lived COM/camera/relay services. No automatic
reconnect or readiness check follows from loading configuration.

v1 adds no configuration file locking, cryptographic signing, Plugin package
snapshots or revision coordination. The separate single-control-session OS
exclusion is an execution ownership rule, not a configuration-version system.

## 7. Coverage

Project defines the complete logical resource set. Environment may bind only a
subset, especially for screens.

Unbound Project resources requested through a wildcard are reported as coverage
gaps. Concrete required resources must be validly bound. A wildcard with zero
valid bindings is rejected rather than passing over an empty set.
