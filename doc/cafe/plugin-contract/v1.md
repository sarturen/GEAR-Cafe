# GEAR Plugin Contract v1

Status: **Frozen for v1 implementation — long-lived Plugin sessions**
Contract id: `gear.plugin/v1`
Date: 2026-09-18

This document is normative. The words **MUST**, **MUST NOT**, **SHOULD**, and
**MAY** describe conformance requirements.

## 1. Scope

A GEAR Plugin supplies hardware/domain behavior to Framework without extending
Framework grammar. One long-lived Plugin session owns its device services;
Workspaces and sequential Runs use those same services.

Exact definitions are in [gear_contracts](../../contracts/README.md). Use its types
without importing Framework internals. Data crosses the boundary as ordinary
dictionaries; services implement the exact shared protocols.

A conforming Plugin package may contain two independently loadable surfaces:

```text
Plugin package
├── Runtime surface      required
└── GUI Workspace        optional for headless-only Plugins
```

The Runtime surface MUST be usable without importing PySide6 or the GUI
Workspace. Framework Core MUST NOT import the GUI surface.

Plugin-to-Plugin calls are forbidden in v1. Shared relations, such as assigning
a camera or relay channel to an ADB device id, pass through Environment data and
the GUI host.

## 2. Responsibility boundary

Framework owns:

- DSL grammar and temporal semantics;
- Run lifecycle and the single-Active-Run rule;
- static Preflight orchestration;
- Environment persistence and Run input archival;
- `PASS`, `FAIL`, and `STOPPED` result semantics;
- callbacks/listeners, reporting, and Framework cleanup;
- the GUI container and Plugin Workspace lifecycle.

Plugin owns:

- Resource Type vocabulary;
- operations, conditions, and evidence capabilities;
- argument schemas and static configuration validation;
- hardware access and device-specific protocols;
- runtime diagnostics and Plugin-owned cleanup;
- one GUI Workspace for all resources managed by that Plugin;
- Plugin-specific configuration, preview, status, and manual controls.

Framework MUST treat Plugin-specific configuration as opaque serializable data.

## 3. Public capability model

The v1 public vocabulary has exactly three capability kinds:

| Kind | Used by | Meaning |
|---|---|---|
| `operation` | DSL `do` | Perform an action. |
| `condition` | DSL `assert` | Evaluate a boolean test predicate. |
| `evidence` | `evidence_on_fail` | Best-effort incident capture. |

Plugins MAY internally distinguish observations, validators, parsers, streams,
or cached state. Those are implementation details. The Framework-facing
assertion surface is always a `condition`.

Capability membership belongs to a Resource Type, never an individual resource
instance. All instances of the same Resource Type MUST expose the same names and
argument schemas. Runtime availability may differ, but the declared vocabulary
may not.

Capabilities MUST NOT add DSL syntax or reinterpret Framework keywords such as
`do`, `wait`, `assert`, `within`, `for`, `every`, or `repeat`.

## 4. Plugin manifest

Every Plugin MUST ship a UTF-8 YAML file named `gear-plugin.yaml` at the package
root.

```yaml
api: gear.plugin/v1
id: gear.relay
version: 1.0.0

entrypoints:
  runtime: gear_relay.runtime:create_plugin
  workspace: gear_relay.workspace:create_workspace

resource_types:
  POWER:
    operations:
      ON:
        args_schema:
          type: object
          additionalProperties: false
      OFF:
        args_schema:
          type: object
          additionalProperties: false
    conditions:
      IS_ON:
        args_schema:
          type: object
          additionalProperties: false
      IS_OFF:
        args_schema:
          type: object
          additionalProperties: false
    evidence: {}
```

Required fields:

| Field | Rule |
|---|---|
| `api` | MUST equal `gear.plugin/v1`. |
| `id` | Stable Plugin id matching `[a-z][a-z0-9]*(\.[a-z0-9_-]+)+`. |
| `version` | Informational Plugin implementation version recorded in Run reports. |
| `entrypoints.runtime` | Required `module:factory` entrypoint. |
| `entrypoints.workspace` | Optional `module:factory` entrypoint loaded only by GUI. |
| `resource_types` | Non-empty mapping of declared Resource Types. |

Resource Type and capability names MUST match `[A-Z][A-Z0-9_]*`.

An entrypoint factory MUST return an object implementing the corresponding v1
protocol. Framework MUST reject duplicate Plugin ids or duplicate ownership of a
Resource Type during registry loading.

v1 does not define dependency solving, remote Plugin installation, hot reload,
or runtime version negotiation. An unsupported `api` value is rejected.

Each Resource Type has one Plugin owner. Adding a capability to ADB means
updating the ADB Plugin. A new independent Plugin declares a new type; it cannot
inject capabilities into another Plugin's type.

### 4.1 Local discovery

The application's fixed `plugins/` directory contains one immediate child
directory per Plugin:

```text
plugins/relay/
  gear-plugin.yaml
  gear_relay/
    __init__.py
    runtime.py
    workspace.py
```

At startup read child directories in lexical name order. Ignore non-directory
entries. A child without a valid manifest is an explicit startup error.
To disable a Plugin move its directory outside `plugins/`; to add one copy it
there and restart GEAR. No registration list or hot reload is provided.

Add each Plugin directory to the Python import path and resolve its declared
`module:factory`. Entry modules must belong to the Plugin's own uniquely named
top-level package. Different Plugins must not share that package name or shadow
Framework, `gear_contracts`, dependencies or standard-library modules.

Importing Runtime and calling its factory must neither import Qt nor open/probe
devices. GUI alone loads Workspace modules. Plugin dependencies must already be
available in GEAR's Python environment; no automatic dependency installation is
performed. Use the one installed `gear_contracts`, not a private bundled copy.

Missing dependencies, broken entries, unsupported APIs, duplicate package names,
Plugin ids or Resource Types stop startup with a diagnostic identifying the
Plugin. Do not silently start with a reduced set.

## 5. Argument schemas and values

`args_schema` uses JSON Schema Draft 2020-12. Schemas must be self-contained:
`$ref` may target only the same schema document. Do not fetch remote schemas.
`default` is documentation, not an instruction to insert missing arguments.
`format` is annotation only; required constraints must be explicit.

A missing `args_schema` is
equivalent to:

```yaml
type: object
additionalProperties: false
```

The schema root MUST be `type: object`; DSL `args` is always a string-keyed
mapping. Plugins use named arguments rather than positional argument arrays.

Framework validates DSL arguments against the declared schema during Preflight.
Plugin MUST still reject invalid direct calls defensively, but MUST NOT rely on
runtime hardware access for schema validation.

Values crossing the contract MUST be serializable as JSON-compatible values:

```text
null, boolean, number, string, array, object with string keys
```

Binary evidence is written to files and represented by metadata; it is never
embedded directly in a contract result. Numbers must be finite.

All v1 YAML files use YAML 1.2 scalar resolution restricted to JSON-compatible
values. ON/OFF are strings, not booleans. Reject duplicate keys, anchors, aliases,
tags, non-string keys and non-JSON scalar values. This also applies to manifests,
Project and Environment files. Reject unknown common envelope fields; Plugin
`config`, argument schemas and diagnostic/result `details` retain their
explicitly assigned ownership and validation rules.

## 6. Environment slice

One GUI Workspace manages one Plugin and all resources assigned to it. The
Workspace receives and commits a complete Plugin slice:

```yaml
plugin:
  id: gear.relay
  config:
    controllers:
      main:
        port: COM7
        channels: 8

resources:
  POWER.kl30:
    type: POWER
    device: ABC123
    config:
      controller: main
      channel: 1
  POWER.kl15:
    type: POWER
    device: ABC123
    config:
      controller: main
      channel: 2
```

If and only if the Plugin declares the `ADB` Resource Type, its slice also owns
the Environment's paper device declarations:

```yaml
devices:
  ABC123: {}
  XYZ789: {}
```

Other Plugin slices omit `devices`. They receive the configured ids through the
Workspace context and may only store one as a resource association.

The GUI host understands only:

- Plugin id;
- logical resource id;
- Resource Type;
- optional `device` association;
- paper device declarations owned by the Plugin that declares `ADB`;
- the distinction between Plugin-level and resource-level `config`.

The Plugin owns the contents of both `config` objects.

Logical resource ids MUST have the form `<RESOURCE_TYPE>.<alias>`. The prefix
MUST equal the resource's declared `type`. Aliases MUST match
`[A-Za-z][A-Za-z0-9_-]*`.

The optional `device` value is a configured ADB serial string used as a paper
identity. It is not a live connection assertion.

## 7. Static configuration validation

The Runtime surface MUST provide:

```text
validate_config(plugin_slice) -> ValidationReport
```

`ValidationReport` contains:

```yaml
status: VALID | INCOMPLETE | INVALID
diagnostics:
  - code: RELAY_CHANNEL_DUPLICATE
    path: resources.POWER.kl30.config.channel
    message: Controller main channel 1 is already assigned.
    details: {}
```

Rules:

- validation MUST be deterministic and side-effect free;
- validation MUST NOT probe hardware, enumerate ports, connect to ADB, open a
  camera, or test link stability;
- `VALID` means the slice is statically executable;
- `INCOMPLETE` means an intentionally unfinished configuration;
- `INVALID` means a contradictory or malformed configuration;
- both `INCOMPLETE` and `INVALID` prevent execution for an involved Plugin;
- validate the complete archived slice, including shared configuration;
- unrelated installed Plugins do not gate a Run;
- diagnostic `code` values belong to the Plugin and SHOULD remain stable;
- `path` is optional but SHOULD identify the relevant configuration field.

Environment may persist all three states. Persistence is not proof of
executability.

Framework additionally validates common outer fields and dangling `device`
references. A referenced device id need only be declared in Environment; it
does not need to be online.

## 8. Runtime protocol

The exact interface is `PluginRuntimeV1` in
[api.py](../../contracts/gear_contracts/api.py), with dictionaries in
[data.py](../../contracts/gear_contracts/data.py). This is a fixed Python interface,
not permission for each implementer to choose different field/method names.

```python
def create_plugin() -> PluginRuntimeV1: ...

class PluginRuntimeV1:
    def configure(self, plugin_slice: PluginSlice) -> None: ...
    def validate_config(self, plugin_slice: PluginSlice) -> ValidationReport: ...
    def begin_run(self, binding: RunBinding, context: RunContextV1) -> None: ...
    def invoke(self, resource_id, operation, args, context) -> OperationResult: ...
    def evaluate(self, resource_id, condition, args, context) -> ConditionResult: ...
    def collect(self, resource_id, evidence, args, context) -> EvidenceResult: ...
    def end_run(self) -> None: ...
    def close(self) -> None: ...
```

The abbreviated annotations above refer to the exact package definitions.
There is no public per-Run ResourceRuntime factory. A Plugin may keep its own
long-lived device/resource objects internally.

The host calls the factory once per Plugin per control session, on its fixed
worker. `configure` receives the saved full slice while IDLE. It accepts
incomplete/invalid Plugin-specific configuration as data; static validation
separately determines executability. It does not open/probe hardware or
automatically reconnect. Changing a physical binding may release the affected
old connection; unchanged connections remain.

`RunBinding` contains exactly:

```yaml
plugin_slice: <complete archived PluginSlice>
resource_ids: [POWER.kl15, POWER.kl30]
```

Resource ids are sorted, unique, and include bound resources used by execution
or evidence. `begin_run` binds the snapshot and resets Run-local observation
cursors/state. It must not conduct readiness probes or start a second Run before
the previous one ends. Capabilities address only the listed resources and use
archived configuration, not mutable GUI state.

Already-open Workspace connections are reused. A capability may open a
configured, not-yet-open connection as part of execution. Failure to open/use
it is an ordinary execution failure. Do not duplicate physical opens merely
because a new case starts. A broken connection is reported; v1 does not
automatically reconnect or retry.

Contexts supply only the exact Run id, artifact directory, stop token, clock,
diagnostic sink and call identities in the package. See
[Runtime context conventions](../framework-runtime/v1.md#5-exact-data-and-context-conventions).
They expose no GUI, Executor, other Plugin instance or service locator.

All public Plugin calls, including creation, validation, configuration and
close, are serialized on the fixed Framework worker. A Plugin may own acquisition
threads but owns their synchronization and lifetime. A long-lived observer must
not retain a finished Run context.

### 8.1 Operation result

```yaml
ok: true
diagnostic: null
details: {}
```

An operation is synchronous from Framework's perspective. It returns after the
requested action succeeds or fails. An `ok: false` result is an execution
failure, subject to Runtime v1's precedence for an already-accepted human stop.

Operation return data is diagnostic only and is not addressable by DSL. A Plugin
that needs result-based behavior MUST expose a semantic condition or make the
operation itself fail according to its declared contract. Framework does not
provide variables or generic stdout parsing.

All result types use the same optional diagnostic shape:

```yaml
code: ADB_DEVICE_OFFLINE
message: Device ABC123 is not reachable.
details: {}
```

`code` is a stable Plugin-owned machine-readable string, `message` is readable
text, and `details` is required JSON-compatible supporting data (use `{}` when
empty). v1 defines no retryable/fatal classification.

### 8.2 Condition result

```yaml
ok: true
satisfied: true
diagnostic: null
details: {}
```

Each call evaluates the declared predicate at that Framework sampling point.
Plugins MAY maintain an event-driven cache, provided `evaluate` obeys the
documented condition semantics.

The Plugin MUST document whether a condition describes current state or events
observed since the previous evaluation. The meaning MUST be stable for every
instance of that Resource Type.

`ok: false` means the condition could not be evaluated and ends normal execution
with FAIL, unless an earlier accepted stop already determines STOPPED.
`ok: true, satisfied: false` is a valid negative observation: an
immediate or `for` assertion fails, while a `within` assertion may sample again
until its deadline.

### 8.3 Evidence result

```yaml
ok: true
artifacts:
  - path: evidence/gear.adb/xxxlog.zip
    media_type: application/zip
    description: DUT diagnostic log
diagnostic: null
```

Evidence paths MUST remain inside the Framework-provided artifact directory.
Evidence collection is best effort. An evidence failure is reported separately
and MUST NOT replace the original Run failure.

### 8.4 Exceptions and cleanup

Plugins SHOULD return structured failures for expected device/protocol errors.
An uncaught Plugin exception after execution begins is captured by Framework.
It causes FAIL unless an earlier accepted stop already determines STOPPED;
Runtime v1 defines that ordering.

Stop is cooperative. Framework does not kill an in-progress Plugin call.
Plugins SHOULD observe the stop token during long-running calls where practical.

`end_run` is idempotent and joins/stops all Run-local work, removes temporary
subscriptions and drops the Run token/context. It preserves session-owned device
connections and passive observers, and must work after partial begin failure.
After a successful return no work from that Run may touch hardware or write
events/artifacts.

`close` is idempotent session shutdown: release all Plugin connections, workers
and handles. Do not implement end_run by calling close. Neither method performs
unspecified DUT recovery.

Use `GearError(code, message)` for invalid boundary states. A Plugin may raise
`StopRequested` only after observing a requested token. All result dictionaries
must have the required shared-package keys; malformed results are Plugin
execution failures, not successful observations.

### 8.5 Session and Run lifecycle

```text
GEAR starts:
  discover -> create_plugin once -> configure saved slice
  -> Workspace can explicitly connect/use devices while IDLE

For each submitted case:
  static validate_config -> human confirmation
  -> begin_run with fresh Run context and archived binding
  -> setup -> body -> normal-success teardown
  -> declared evidence after execution FAIL
  -> end_run
  -> Framework finishes reporting and completely exits the Run task
  -> IDLE, with the same session and device connections

GEAR exits:
  finish active Run/manual work -> dispose Workspace -> close Plugin session
```

A rejected/declined submission never calls begin_run and does not close the
session. Every attempted begin_run, including partial failure, receives end_run.
Framework attempts remaining cleanup if one Plugin cleanup fails. Runtime v1
then blocks the session, preserving original execution result and ordered errors;
a provisional PASS becomes FAIL.

A relay Plugin may share one COM connection across channels. A camera Plugin may
share acquisition between preview and conditions. Both GUI and Runtime use that
same Plugin-owned service. Framework does not model that private sharing or
coordinate a handoff between separately opened connections.

## 9. GUI Workspace protocol

The GUI entrypoint receives its own long-lived session and a Workspace context.
It returns a WorkspaceV1 containing one widget:

```python
def create_workspace(
    context: WorkspaceContextV1,
    runtime: PluginRuntimeV1,
) -> WorkspaceV1: ...
```

`WorkspaceV1.widget` must be a PySide6 QWidget. The shared package annotates it
as object to avoid a Qt dependency. `dispose()` is an idempotent GUI-thread
method that removes UI subscriptions, timers and preview consumers, without
closing the shared Plugin session. Factory creation, widget operations, disposal
and all Workspace listeners run on the GUI thread.

The page may contain sub-tabs/panels, but the host creates one top-level page.
Tab changes do not dispose the Workspace or release its device connections.

The Workspace may provide, as appropriate:

- resource creation, removal, aliasing, and device association;
- Plugin-specific configuration;
- device discovery as a convenience;
- camera preview and persisted ROI drawing;
- serial and ADB input/output;
- physical and logical relay status/control;
- live connection/status display.

The host does not generate a universal form for these features.

Idle-time manual actions use the same session's private services. The Workspace
passes a closure to `context.submit_manual`; the host executes it on the worker
and returns its result on the GUI thread. It does not enter Executor or create
a Run. The closure may access only its own Plugin, not other Plugins.

Private manual methods are agreed within the Plugin's own Runtime/Workspace
implementation; Framework does not interpret their names, arguments or data.
Never call hardware-driving methods directly on the GUI thread. A passive
preview may read the Plugin's synchronized cache during an Active Run.
Runtime remains importable without GUI dependencies.

### 9.1 Workspace context

Use the exact package interface:

```python
class WorkspaceContextV1:
    def current_slice(self) -> PluginSlice: ...
    def configured_device_ids(self) -> list[str]: ...
    def commit(self, full_slice, validation_report) -> None: ...
    def run_state(self) -> Literal["IDLE", "ACTIVE"]: ...
    def subscribe_run_state(self, listener) -> Subscription: ...
    def subscribe_environment(self, listener) -> Subscription: ...
    def submit_manual(self, action, listener) -> None: ...
```

`configured_device_ids` is derived from saved Environment declarations. It is
not derived from the live `adb devices` result.

`current_slice` returns a detached copy. Run-state listeners receive one IDLE
or ACTIVE string. Environment listeners take no arguments; re-read slice/device
choices. Neither replays past changes. Subscribe then read current state on the
GUI thread. Unsubscribe is idempotent; dispose all UI-owned subscriptions.

Environment notifications do not authorize rewriting another Plugin's slice.

`submit_manual` accepts a zero-argument callable returning JSON-compatible data.
It raises BUSY during ACTIVE. Accepted idle work is serialized before subsequent
Runs; submit while manual/configuration work remains is rejected, not queued.
`listener(ManualResult)` runs once on the GUI thread with a value or exception
diagnostic. Manual failures are displayed locally and are not test results.
Listeners return promptly; callback exceptions do not change Run outcomes.

### 9.2 Real-time commit

There is no global edit mode, Save/Cancel workflow, or unsaved-dirty state.

The Workspace MUST call `commit` after a semantic configuration change:

- selection, alias, association, or mapping changes commit immediately;
- ROI commits when one drawing/drag gesture completes;
- free text commits on Enter, focus loss, or a short debounce;
- preview frames, received serial data, status changes, and manual commands do
  not commit configuration.

Each commit replaces the complete slice; no field patches or merge protocol.
The GUI-thread host validates common fields/ownership, then persists atomically.
Reject ACTIVE with BUSY even if a widget failed to disable editing. Invalid
outer structure/ownership raises INVALID_SLICE. Write failure raises
PERSISTENCE_ERROR, leaves the saved/current slice unchanged and is shown to the
user. Never publish a successful change before persistence.

After success, schedule configure on the worker and notify Workspace listeners.
No Run is accepted until configuration application finishes. Plugin-specific
semantic INCOMPLETE/INVALID may be saved; malformed common envelopes may not.

For the Plugin that declares `ADB`, the complete slice includes device
declarations. GUI host rejects `devices` changes from every other Plugin.

The Workspace-supplied validation report supports immediate display only.
Preflight calls Runtime `validate_config` again and remains authoritative.

An incomplete or invalid slice may be committed and displayed. Preflight, not
persistence, gates execution.

### 9.3 Active Run behavior

During an Active Run, Plugin Workspace configuration and manual controls MUST be
read-only. Status display MAY continue.

ACTIVE begins at accepted submission and lasts through confirmation, execution,
evidence, Run-local cleanup, report writing and complete Run-task exit.
Rejection/decline also completes submission cleanup before IDLE. A known result
alone never releases ACTIVE. Finalization failure keeps the session blocked and
Workspace ACTIVE until exit/restart. Host-side commits/manual calls enforce the
boundary with HOST_BLOCKED for a blocked session.

Session connections and passive acquisition/status may stay active. They must
not change bindings, inject manual commands or perform unspecified recovery.
There is no cross-process connection handoff, automatic reconnect, ownership
arbitration system or separate Plugin GUI process. Runtime uses archived inputs.

### 9.4 Device identity behavior

An ADB serial is a manually configured paper identity:

- offline status does not remove or invalidate the identity;
- live discovery never rewrites Environment automatically;
- changing or deleting a device id does not cascade into other Plugin slices;
- dangling associations remain saved and visible;
- users manually reconfigure affected resources;
- static Preflight rejects dangling associations.

## 10. Relay-specific required invariants

The generic Framework has no shareability topology. A Relay Plugin that models a
multi-channel controller MUST enforce these rules itself:

- one controller connection may expose many physical channels;
- each physical channel maps to at most one logical `POWER` resource;
- each logical `POWER` resource maps to exactly one physical channel when valid;
- a channel belongs to at most one configured device id;
- no aliasing or multiple logical bindings to the same channel is permitted.

Its Workspace SHOULD expose two synchronized views of the same state:

- physical: controller/COM, channel count, state, and per-channel control;
- logical: device id, KL15/KL30 resource, state, and control.

Unbound physical channels remain visible in the physical view. Unknown hardware
state is displayed as `UNKNOWN` rather than guessed.

## 11. Conformance checklist

A Plugin is v1-conforming when:

- `gear-plugin.yaml` is valid and uses `gear.plugin/v1`;
- Resource Types and capabilities are explicit and schema-valid;
- every instance of one Resource Type exposes the same capability contract;
- Runtime imports without GUI dependencies;
- static validation performs no hardware access;
- Runtime uses only its binding and Framework-provided contexts;
- results and diagnostics follow the v1 shapes;
- Run cleanup and session shutdown are separately idempotent;
- two sequential Runs reuse a session/connection and reset Run-local state;
- all public calls obey the fixed-worker rule and Workspace callbacks use GUI thread;
- no Run or manual command starts before preceding Run finalization/exit;
- any GUI surface is one Workspace for the whole Plugin;
- Workspace replaces its full slice on semantic changes;
- Workspace becomes read-only during an Active Run;
- the Plugin never calls another Plugin directly;
- automated tests cover manifest loading, schema validation, configuration
  validation, each capability's success/failure result, and cleanup.

## 12. Explicit non-goals

v1 does not provide:

- Plugin-to-Plugin dependency injection;
- per-instance capability negotiation;
- universal generated configuration forms;
- field-level configuration patches;
- hot reload or remote Plugin installation;
- Plugin process isolation;
- automatic hardware readiness checks in Preflight;
- automatic recovery, retry, or connection handoff;
- general event bus or message broker;
- generic shareable/exclusive resource graphs.
